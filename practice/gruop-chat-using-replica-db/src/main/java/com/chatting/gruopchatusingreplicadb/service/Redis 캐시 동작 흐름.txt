1. 메시지 쓰기 요청(Postman -> 서버_
  - 사용자가 Postman으로 메세지를 서버로 보낸다 {"username" ; "user1", "content" : "hello"}
  - 서버(MessageService.sendMessagetoAll)가 요청을 받아 DB에 저장한다
  - 저장이 성공하면, @CacheEvict 어노테이션이 동작해서 캐시(message cache)를 전부 "지운다"


2. 메시지 저장(서버 -> DB)
  - 서버는 메시지를 DB에 직접 저장한다
  - 이 과정에서 DB는 캐시를 "직접 알지 못한다" (DB와 Cache는 서로 독립적인 시스템이기 때문이다)
  - 대신 @CacheEvict이 동작하여 DB 저장이 끝나면 캐시를 클리어한다 (DB가 캐시를 "갱신"하는게 아니라, 캐시를 비워버려서 다음 조회가 강제로 DB를 보게 만드는 방식)


3. /last 명령 (최신 메시지 조회)
  - 사용자가 /last 명령을 보내면:
    - MessageService.getLastMessage() 실행
    - 이 메서드는 캐시를 사용하지 않고 DB에서 직접 조회한다
    - 이유: "가장 최근 메시지"는 반드시 DB가 기준이어야 하며, 캐시에 오래된 값이 있을 수도 있기 때문이다
  - 따라서 /last는 DB에서만 읽고, 캐시는 건드리지 않는다.


4. /get (number} 명령 (특정 메시지 조회)
  - 사용자가 /get 5 같은 요청을 보내면:
    - MessageService.getMessage(5) 실행
    - 여기는 @Cacheable이 붙어있어서,
      1. 먼저 Redis 캐시에서 message : 5 키를 찾아본다
      2. 캐시에 있으면 바로 반환
      3. 캐시에 없으면 DB에서 조회 후 자동으로 캐시에 저장
    - 즉, 자주 조회되는 메시지는 DB를 매번 치지 않고 캐시에서 빠르게 읽을 수 있다.


 5. /exception 요청 (강제 예외 발생 -> 롤백 확인용으로 만든 것)
   - 사용자가 /exception을 보내면:
     - 내부적으로 DB 저장 로직에서 예외를 일부러 발생시킨다.
     - 그럼 트랜잭션이 롤백되므로 DB에 아무것도 일어나지 않음
     - 이 경우 캐시도 건드리지 않음(DB에 변화가 없으니 캐시 무효화도 할 필요가 없음)
   - 즉, 예외가 발생하면 DB와 캐시는 그대로 유지된다.  


# 어노테이션 설명
✅ @Cacheable
    캐시에 있으면 DB를 안 거치고 캐시에서 바로 리턴.
    캐시에 없으면 DB에서 읽고 캐시에 저장.
    value = "message" → 캐시 저장소 이름(보통 Redis에서 키 prefix 역할).
    key = "#messageSequenceId" → 캐시 키. 예: message:5.
    unless = "#result == null" → 결과가 null이면 캐시에 저장하지 않음.
👉 주로 읽기 최적화에 사용.


✅ @CacheEvict
    캐시를 지우는 역할.
    value = "message" → 어떤 캐시 저장소를 지울지 지정.
    allEntries = true → 해당 캐시 저장소의 모든 키를 다 지움.
    이유: 메시지가 새로 추가되었으니 “특정 메시지” 캐시들이 최신이 아닐 수 있기 때문.
    보통 쓰기 직후에 사용.
👉 주로 쓰기 후 캐시 무효화에 사용.




postman이 있고 server가 있고 DB와 Cache가 있는 상황이다.
1. postman을 이용해서 서버로 메시지를 보내면(write)
2. 서버에서 DB로 보내 DB에 써질거고
3. DB가 Cache에 Clear를 보낼거다. (리딕션?을 보내서 초기화 시킨다)
4. postman에서 /last로 가장 최신 메시지를 읽으려고 read 요청을 하면 DB에서만 조회해서 보내줄거고(Cache 안건들임)
5. /get number로 메시지를 조회하면 Cache에서 조회한다. cache에 없으면  cache 어노테이션이 자동으로 DB에서 조회한 다음에 cache에 채워주고 리턴한다. 그래서 다음에도 조회 요청이 들어오면 cache에서 바로 리턴한다.
6. /exception 요청하면 강제로 예외를 발생시켜서 rollback을 시킨다. rollback을 시키면 DB에는 변한 게 없으니까 Cache를 건들이면 안된다. 이 상황에서 Cache에는 그대로 남아있는 걸 기대하는 거다.
